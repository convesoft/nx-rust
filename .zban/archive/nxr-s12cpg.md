Goal: tasks of one group run with one cargo call for each step of their target, each with its own result and cache entry.

Implements `REQ-BATCHING` and `DES-BATCH` (`nx-rust/docs/execution.mara.md`). Checked by `VER-BATCHING`.

- [x] `batchImplementation` in `executors.json` for both executors; `preferBatch: true` moves to nxr-8f9dz2 (see "Staging" below)
- [x] `build` and `doc` run `@convesoft/nx-rust:cargo-outputs`, a second entry of `executors.json` with the same implementation and schema (`preferBatch` with nxr-8f9dz2) (`DES-BATCH`, "Two batch executors"; `DES-TARGETS`, "Executors"): the inferred targets name it, `init` adds its empty `targetDefaults` entry through `DES-GENERATORS`, `DES-TARGET-DEFAULT-GUARD` compares its targets, and each `test` task of a batch runs the guard of `DES-TARGETS` ("Guard") before the batch's cargo calls, failing only that task. Covers the parts of `VER-BATCHING` about the two executors and stored `build` entries
- [x] Grouping by kind of task, workspace, feature set, profile and target triple; groups run one after another
- [x] One cargo call per step of the group's target (`DES-BATCH`), every step selecting the crates the same way; the output of every step mapped to a result and terminal output per task
- [x] Select the group's crates as `DES-INVOCATION` says: `crateSelection` in `nx-rust/src/executors/command.ts` (`-p` and each crate's package ID specification, the package name for `cargo fmt`), with the specifications from one `memberSpecs` call (`nx-rust/src/cargo/package-specs.ts`) per group, in the workspace root with the group's environment. Never a bare name or `name@version`: several `-p` make a shared name ambiguous where one crate alone does not (`EVD-CARGO-PACKAGE-SPECS`). Map cargo's list of failed targets, which names members by their bare names, back to tasks by package name
- [x] In a verbose run, print each step's cargo command as `DES-INVOCATION` ("Printing the command") says for a batch, with `nx-rust/src/executors/cargo-invocation.ts`. Decide once per batch with `batchRunsVerbosely(process.env)`, the batch process's own environment, never with `taskRunsVerbosely`, whose `context.isVerbose` is always `false` in a batch, and never with a task's environment that the batch rebuilds from dotenv files, where a crate's `.env` can disagree with the run (`EVD-NX-24-VERBOSE`). Build the lines with `commandBlock` from the step's `CargoInvocation`, the one cargo is started with (`cargoEnvironment`), with the tasks of the command as the name in the first line. The batch process writes the lines itself, once per command and before it starts, into no task's `terminalOutput`, so that Nx neither stores nor replays them (`EVD-NX-24-BATCHES`). Test a verbose batch, one with `--verbose=false`, and one where the root `.env` sets `NX_VERBOSE_LOGGING=false` and a crate's `.env` sets it to `true`
- [x] The directory check of cached `build` and `doc` (`DES-OUTPUTS`) once per group
- [x] `--keep-going` and `--no-fail-fast`; a task succeeds only where cargo's output shows that its crate passed (`DES-BATCH`): the JSON artifacts of builds, checks and clippy, and the list of failed targets of `cargo test` (`DES-TEST-RUN`); a test step stopped by a compile error fails every test task with a message naming the crates that did not compile; a failure outside the selection is a warning
- [x] Each task of a batch ignores the options that its target does not take, with its lines, as a single task does: call `taskOptions` (`nx-rust/src/executors/task-options.ts`) once per task, with `taskGraph.tasks[id]` as its graph task, its target's options and active configuration as `configured`, and `recordedNxCommand()` as the record; pass only `options` to the grouping, so that an ignored option splits no group, and put `warnings` at the top of the task's own terminal output. Covers the group case and `--batch=false` of `VER-UNKNOWN-OPTIONS` (two crates whose `project.json` files give an unknown option different values share their cargo commands)

Done when: the parts of the cited verification that cover this work pass, and `pnpm nx run-many -t build lint test` and `pnpm nx format:check --all` pass.

Note: `EVD-NX-24-BATCHES` records how Nx 24.0.6 treats a batch's results, terminal output, environment and cache entries; the implementation follows it.

## Staging

Decided by the control plane on 14 November 2026 under `GOAL-TRUSTED-CACHE`: `ADR-WORKSPACE-FEATURES` lets crates share a cargo command only where a strategy resolves features for the whole workspace, and none exists before nxr-8f9dz2 (`workspace-build`) and nxr-k64tm5 (`hakari`, `cargo`). Until then:

- The batch executor exists with everything listed above, and every task forms a group of one crate ("Groups of one crate" in `DES-BATCH`): one cargo command per step per crate, exactly the command the task runs on its own, with today's results and keys.
- `preferBatch` stays off, so that a plain `nx run-many` runs tasks as in milestone 0.1. The batch executor runs when Nx is asked to batch (`--batch`), which is how the tests reach it.
- The code that runs a group of several crates is written and tested with real cargo through `runGroup` (`nx-rust/src/executors/group-run.ts`), with groups that the tests form. The one switch that nxr-8f9dz2 turns on is `groupsShareCommands` in `nx-rust/src/executors/groups.ts`; turning on `preferBatch` moves to nxr-8f9dz2 as well. The status note of `nx-rust/docs/execution.mara.md` says what is in effect.

## Summary of Changes

- The batch implementation of `DES-BATCH` (`nx-rust/src/executors/batch.ts`) for `@convesoft/nx-rust:cargo` and the new `@convesoft/nx-rust:cargo-outputs`, which `build` and `doc` now run; `init` adds its empty `targetDefaults` entry, and the guard judges each executor's entries for its own targets. One result per task, streamed per group, never a throw; every task runs the checks of a task on its own before any cargo call, with its own options, warnings, environment (Nx's `getTaskSpecificEnv`, `task-env.ts`) and executor context, the guard of `test` after `build` included.
- Grouping in `groups.ts` (kind, workspace, command options and environment, ignored options splitting nothing), groups run in waves that respect the dependencies inside the batch, a task whose dependency failed is reported skipped; one report of the directories and one of the members per group (`groupInvocations` in `task.ts`, `memberPackages` in `package-specs.ts`).
- `runGroup` (`group-run.ts`) and `cargo-output.ts`: one command per step, output in order, per-task output and result, the post-check and the build input check for each task whose crate passed; for several crates `--keep-going`, JSON messages and `--no-fail-fast`, units read from the JSON artifacts, failed test targets mapped back by package name, a compile error in a test step failing every test task of the step.
- Staging as above: production forms groups of one crate and `preferBatch` stays off; `groupsShareCommands` and `preferBatch` move to nxr-8f9dz2, whose task list says so. The status note of `execution.mara.md` says what is in effect.
- Knowledge: `DES-BATCH` counts units, not targets, after the experiment now in `EVD-CARGO-BATCH-FAILURES` (a broken dev-dependency leaves out a crate's test units only), and says what a group of one runs; the guides of `setup.mara.md` and `targets.mara.md` and `VER-SETUP` name the fourth executor and what the rename does to existing `targetDefaults`.
- Tests: `batch-runs.spec.ts` (through Nx with `--batch`, fixture `batch-groups` and `binary-tests`), `group-run.spec.ts` (groups of several crates with real cargo), `unknown-options.spec.ts` with `--batch`, the upgrade case in `target-defaults.spec.ts`; ten mutations each failed the test that covers them.

Fourth independent review of 9511488, a short round that the control plane verifies itself; five points fixed on the branch, after local `main` 9b21a57 and 5acde83 were merged. (1) The vault check stood behind an early return: with no plain dotenv file, a root `.env.vault` and `DOTENV_KEY` in the command, Nx's removal of the root values reads the vault and the task got `REVIEW_VAULT=secret`. `dotenvProblem` now checks the vaults first, `.env.vault`, `.local.env.vault` and `.env.local.vault` at the root with or without the plain file and the vault beside the task's last file, before the files that define `NX_LOAD_DOT_ENV_FILES`, before the return for a task without files and before the one where Nx loads none; the other early returns, no `$` and another dotenv-expand version, come after it. (2) The limit of 256 lookups failed 257 `http://${HOST}:…` entries with `HOST` from the command. The lookup and step limits are replaced by bounds that tell a recursion from a repetition: an exact cycle (Brent's algorithm), more than 64 nestings of a name's value inside its own earlier insertions along one chain, a result beyond 131,072 characters (Linux's `MAX_ARG_STRLEN`), and 1,000,000 steps of the check's own search, given as the check's own uncertainty. `DES-BATCH` states why an expansion that ends within the size of one environment variable reaches none of the first three. Finished expansions in 12,500 generated cases nested a name at most five times, and none of 1,012 skipped cases ended in Nx's own loader. (3) The drift test's nx process starts with `NX_ORIGINAL_FORCE_COLOR=0` and `NO_COLOR=1` in place of `FORCE_COLOR=0`, so seed 20261815 runs. The generator writes root vaults alone and beside plain files and lists of 150 to 400 references, and the test requires cases of each. `VER-BATCHING` says that a skip means the check's budget ran out, with no proof either way about dotenv-expand, and counts 468 of 2,500. (4) The message for a file that defines `NX_LOAD_DOT_ENV_FILES` says to remove the definition from the named files and, to switch the loading off, to set `NX_LOAD_DOT_ENV_FILES=false` in the environment of the `nx` command, in the shell or the CI settings; so do `DES-DIAGNOSTICS` and a new user section on dotenv files in `execution.mara.md`. (5) The batch's heap exhaustion was small to fix: while Nx builds a task's dotenv layer, the batch gives each of Nx's run-dependent variables that the task's files define a value of its own and restores its environment afterwards, so dotenv-expand takes it as it is, as the `nx` process takes its own. `EVD-NX-24-BATCHES` ("Dotenv expansion") records the findings. Each fix has a test that failed against a mutation: the vault check behind the early returns, a restored lookup limit, the old message, no shield (the batched run ran out of memory), and a start environment without `NX_ORIGINAL_FORCE_COLOR`. A test that came from `main` with nxr-vnb0ph expected `build` to run `@convesoft/nx-rust:cargo`, and now expects `@convesoft/nx-rust:cargo-outputs`. Rejected this round: a bound on the first repetition of a name inside its own insertion (16 of 316 such cases end in Nx), a lookup limit per name, a global limit of 10,000 steps, a projection detector (it missed suffix growth and was slow), one regular expression per earlier result (it exhausted the heap), and a budget on paths as the only control of branching.
