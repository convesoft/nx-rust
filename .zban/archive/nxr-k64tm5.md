## Summary of Changes

Graph creation chooses each workspace's strategy (`workspaceStrategy` in `nx-rust/src/graph/unification.ts`): `cargo` and `workspace-build` where the settings say so, unchecked; otherwise `hakari` where `.config/hakari.toml` or `.guppy/hakari.toml` parses, names a member as the hack crate and passes the four checks of `DES-UNIFICATION`, and `workspace-build` with the fallback warning on every project of the workspace elsewhere (none for a workspace without a configuration and without a setting). Under `hakari` a non-host triple that graph creation knows and `platforms` does not list draws its own warning. The strategy and `platforms` go into the projects' metadata, the inputs (`hakari`: own digest, the hack crate's manifest and the configuration in place of the other members' manifests and of the crates outside the workspace), the `hakari-check` target of the workspace project (run by the lockfile executor, depending on the lockfile task, with the crates' cached targets and `doc` depending on it, renamable through `targetNames`), `test`'s wait for `build` (own crate only under `hakari` and `cargo`), and `init`'s table of tools. The executor selects with `-p` under `hakari` and `cargo`, with groups of one crate for feature flags and unlisted triples or hosts under `hakari` and for `--features` under `cargo`; passes `--config 'resolver.feature-unification="workspace"' -Zfeature-unification` on every compiling command under `cargo`; fails a crate task without its dependency on `hakari-check` before cargo; runs `cargo hakari generate --diff` and `manage-deps --dry-run` for `hakari-check`, with the message to regenerate; and lets no build group of a batch rewrite a crate's stored files after that crate's task ran (`writesStoredFiles` in `batch.ts`, now per crate). The check of several entries needed no change: the maintainer's rule refuses overlapping entries whatever their options; the status note no longer mentions it. The strict per-crate build target moved to nxr-ys8rx5 (provisional note in `DES-UNIFICATION`, evidence in `EVD-HAKARI-UNIFICATION`, "Without the hack crate").

Tests: `hakari-graph.spec.ts` (33 cases: each check, its warning, the accepted settings, settings precedence, triples), `hakari-runs.spec.ts` (14 cases with real cargo and Nx: the central experiment with unchanged units, features and hash, one `cargo test` for a group, feature flags and triples per crate, the fallback at task time and the earlier keys after undoing it, the missing `hakari-check` dependency, the post-check of a shared group, the drift cases and the offline case with the real cargo-hakari 0.9.39, the missing tool, the `cargo` strategy on stable), new rows in `cache-keys.spec.ts`, `lockfile-keys.spec.ts`, `lockfile-runs.spec.ts`, `configuration.spec.ts` and `init.spec.ts`. The cases that need cargo-hakari skip without it (`NX_RUST_TEST_CARGO_HAKARI` or `PATH`).

Checks on the merged head (local `main` 4626c4f): `NX_DAEMON=false pnpm nx run-many -t build lint test --skip-nx-cache` with the real cargo-hakari, 58 suites, 1825 passed, 1 todo; `NX_DAEMON=false pnpm nx e2e nx-rust-e2e --skip-nx-cache`, 27 of 27 on Cargo 1.100.0 and 27 of 27 on 1.91.0 through a private `RUSTUP_HOME`; the hakari specs on 1.91.0, 46 passed, 1 skipped (no musl target for 1.91.0). On the final head: the same run-many again, `pnpm nx format:check --all`, `mara schema validate`, `mara project validate` (valid, evaluation complete) and `zban check`.

Rejected: a `[patch]` on the command line to build without the hack crate (cargo refuses to replace a member); checked-in fixtures generated by cargo-hakari (the third-party crate is a git repository made per test, whose URL the hack crate names; the harness writes the files as 0.9.39 generates them, which `hakari-check` with the real tool confirms).

## Summary of Changes after the control plane's checks

The missing-tool case of `hakari-runs.spec.ts` depended on cargo-hakari being absent from the machine's `PATH`. It now hides whatever is installed, through an empty `PATH` folder with links to the toolchain's cargo and rustc and an empty Cargo home (as `missing-tools.spec.ts` hides the other tools), asserts that the tool is hidden, and runs a stand-in through the same environment. `cargoHakariFolder` in the test harness finds the real tool as cargo finds a subcommand: `NX_RUST_TEST_CARGO_HAKARI`, then `PATH`, then the Cargo home's `bin`. Checks: the hakari specs with the real cargo-hakari 0.9.39 first on `PATH`, 47 of 47 on Cargo 1.100.0 and 46 passed, 1 skipped (no musl target) on 1.91.0; `NX_DAEMON=false pnpm nx run-many -t build lint test --skip-nx-cache` without the tool, 58 suites, 1820 passed, 5 skipped, 1 todo, and with it on `PATH`, 1825 passed, 1 todo; `pnpm nx format:check --all`; `mara schema validate`, `mara project validate` (valid, evaluation complete); `zban check`.
