Goal: no `build` task can store another crate's executable under its key because two crates of one artifact directory have binaries with the same file name (`GOAL-TRUSTED-CACHE`).

Context: `RISK-ARTIFACT-DIR-WRITERS` ("Executables with one file name") and `EVD-CARGO-ARTIFACT-WRITERS`: cargo writes the binaries of both crates to the same path, warns of an output filename collision when one call builds both, and the file is that of the crate it built last. `DES-OUTPUTS` declares that path as an output of each crate's `build`, so either entry can hold the other crate's executable whatever the order of tasks. `DES-BUILD-INPUT-CHECK` already leaves such shared record names unread (`sharedRecordNames` in `nx-rust/src/graph/build-records.ts`). Ordering tasks cannot fix it: it needs a rule when the graph is created.

Decided by the control plane on 14 November 2026, recorded in `RISK-ARTIFACT-DIR-WRITERS`: the `build` targets of crates whose executables share a file name in one artifact directory are left uncached, with a keyed project warning that names the crates and the file and says to rename one binary. Graph creation does not fail: cargo itself builds such a workspace, with its own warning, and the plugin must not make a valid Cargo workspace unusable (`REQ-CARGO-UNCHANGED`), while an uncached `build` can store no wrong entry (`GOAL-TRUSTED-CACHE`).

- [x] Reproduce with two crates of one workspace, and of two workspaces with one artifact directory, whose binaries share a name
- [x] Write the rule into the design: a reason in `cargo.uncached` (`DES-OUTPUTS`, "Per project"), the warning row in `DES-DIAGNOSTICS` (a project warning whose digest the keys hold, "Warnings where they are seen"), and a check in `VER-CARGO-UNCHANGED`
- [x] Implement it at graph creation, for crates of one workspace and of several workspaces that share an artifact directory, with tests that the colliding `build` targets are uncached and warn, that the other targets and crates stay cached, and that graph creation succeeds
- [x] Update `RISK-ARTIFACT-DIR-WRITERS` ("Executables with one file name") once implemented

Done when: the decided rule is accepted in Mara, implemented and tested, and `mara project validate` reports `valid: true`.

## Summary of Changes

- Graph creation compares, per artifact directory (workspaces linked as for `doc`, members without a project included), the executables of binaries and the files of `cdylib`, `dylib`, proc-macro and `staticlib` libraries; names that differ only in case or Unicode normalisation count as one on every host, and triples and profiles play no part. A crate whose `build` declares such a file gets `build` uncached as a whole, and its `test` too where the file is a binary's executable and `cargo test` builds its binaries (its tests run that file as `CARGO_BIN_EXE_<name>`). Other targets stay cached, as does a `dylib` or proc-macro crate's `build`, which does not declare its file. Graph creation does not fail; one keyed project warning per shared name names the crates, the file, the artifact directory and the uncached targets, and says to rename one binary or library. A `project.json` that caches such a target fails its task before cargo runs, and a `targetDefaults` entry fails graph creation, as for every target the plugin leaves uncached. The edge from `test` to `build` stays. Code: `nx-rust/src/graph/artifact-names.ts`, wired into `nx-rust/src/graph/caching.ts`.
- Knowledge: `DES-OUTPUTS` "Files of one name", the `DES-DIAGNOSTICS` row, checks in `VER-CARGO-UNCHANGED`, a pointer in `DES-BUILD-INPUT-CHECK` ("A shared name"), `RISK-ARTIFACT-DIR-WRITERS` (the bullet now holds what remains; rating unchanged), measurements in `EVD-CARGO-ARTIFACT-WRITERS`, and the caching guide.
- Measured: with the comparison taken out, 7 of 16 stored `build` entries held the other crate's executable; with it, all 16 builds ran and left their own crate's executable. On cargo 1.100.0 and 1.91.0, an integration test failed with the other crate's output when that crate's `cargo build -p` ran during `cargo test -p`.
- Tests: `nx-rust/test/shared-executables.spec.ts` with the new fixture `shared-executables`. With the comparison disabled, 12 of 15 fail; the 3 negative rows fail when it over-matches.
- Checks run on the final tree, after both reviews' fixes and merging the local `main` at 235ef48: `pnpm nx run-many -t build lint test` (44 suites, 1421 passed, 1 todo), `pnpm nx format:check --all`, `pnpm nx e2e nx-rust-e2e` on cargo 1.100.0 (27 passed) and on 1.91.0 through a private `RUSTUP_HOME` (27 passed), `mara schema validate`, `mara project validate` (`valid: true`, evaluation complete, no errors or warnings) and `zban check`.
- Rejected: a target-scoped warning printed only by the tasks of `build` and `test` (the issue asks for a project warning whose digest the keys hold, like the other artifact-directory warnings); splitting `build`'s outputs to leave out the shared file (one cargo command writes them all, and a cache hit would miss a file the task writes); folding case only on macOS (Linux and macOS would get different graphs).
- Filed nxr-r83zq5, comparing artifact directories of workspaces that separate plugin entries receive, and closed it in this branch after the review (below).

## Changes after the review

- Separate plugin entries: with two or more entries of the plugin, each entry also reads the workspaces that the others receive (`otherEntriesWorkspaces` in `entries.ts`, `discoverReportedWorkspaces` in `discovery.ts`), so that `doc` sharing, files of one name and shared record names compare the workspaces of every entry, and every entry reaches the same verdict; the shared-name warning is printed by the entry that holds the first crate's workspace. Option (b), a check when the task starts, was not needed: (a) works with Nx 24.0.6 with plugin isolation on and off, through the entry context that `checkEntries` already uses. Cost: no extra cargo call without isolation, one `cargo metadata --no-deps` per workspace of the other entries in each isolated worker, no time difference beyond the spread.
- Nested artifact directories: two artifact directories count as one where they are the same or one lies inside the other (folded real paths), for `doc` as well. Every file that `build` declares lies one or two folder names (triple, profile) below its directory, so outputs of two different directories can meet only where one lies inside the other: this covers whatever triple or profile a target table, `project.json`, configuration or the command line gives, without reading options. The check of "Triples that only a task picks" does not cover a command-line triple (it concerns runs that name no triple), and with this rule it does not need to.
- Tests: the reviewer's two configurations as graph tests (isolation on and off) and run tests; with other entries' workspaces left out, the three two-entry tests fail; with only equal directories counted, the three nested tests fail; both run tests then fail because the second run restored both builds.

## Changes after the second review

- A check when a cached task starts, beside the graph-time comparison (`sharedArtifact` in `nx-rust/src/executors/shared-artifacts.ts`, called from `taskInvocation`): a cached `build`, `doc`, or `test` that waits for its `build`, fails before cargo runs where a target of another project in the project graph, whichever installation of the plugin created it, has an artifact directory that is the task's or nested with it and writes a file of a name the task declares (for `doc`: another `doc` target), naming both targets and the file. Each crate's `build` now records its files in `metadata.cargo.artifactFiles`. It matches only pairs that graph creation would leave uncached, so it fails no task where graph creation saw everything; about 2.6 µs a task on `release-crates`. The reviewer's configuration is a test with a real second installation: a copy of the compiled plugin as `node_modules/rust-alias`, registered under that name.
- Overlapping entries: the first entry of the plugin by its place in `nx.json` that receives a project attaches its warnings (`warnings`, `configurationWarnings`, `targetWarnings`), and a warning is printed by the first entry that receives a project it concerns (`entryView` and `warnsHere` in `entries.ts`), replacing the earlier "first crate's workspace" rule. Two entries with the same options that receive the same manifests cannot be told apart and still both attach and print. The other duplicates of overlapping entries (target metadata lists, Nx's `technologies`, discovery's printed warnings, mixed options) are filed as nxr-v1b7rc, which needs a decision.
- `cargo doc` refuses a workspace whose binaries share a name (both cargo versions), so the workspace's `doc` fails as plain `cargo doc` does; recorded in `DES-OUTPUTS`, the evidence and the guide.
- Mutations: without the task-start check, the alias test fails (`alpha:build` builds); with every entry attaching, both overlapping tests fail on the metadata; with every entry printing, both fail on the printed count.
