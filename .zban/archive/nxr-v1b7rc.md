Goal: a repository whose `nx.json` has two entries of the plugin whose `include` and `exclude` both let a workspace's manifests through (such as `"plugins": ["@convesoft/nx-rust", {"plugin": "@convesoft/nx-rust", "include": ["rust/**"]}]`) gets each project, its targets and its metadata as one entry would give them, or a decision says what such a configuration means.

Context: each entry's `createNodes` creates the same projects, and Nx merges them: `mergeMetadata` in Nx 24.0.6 (`dist/src/project-graph/utils/project-configuration/target-merging.js`) appends lists two levels deep. Measured on the fixture `shared-executables` with those two entries (review of nxr-ew8kb3), with plugin isolation on and off: every target's `metadata.technologies` held `cargo` twice, `metadata.cargo.triples` of `build` and `doc` twice (five times without isolation), `metadata.cargo.digests` twice and on the workspace's `doc` six or nine times, the lockfile task's `members` likewise; `gamma:build`, `gamma:check` and `beta:test` still passed. nxr-ew8kb3 makes only the first entry that receives a project attach and print its warnings (`EntryView` and `warnsHere` in `nx-rust/src/graph/entries.ts`, `DES-DIAGNOSTICS`), so `metadata.cargo.warnings`, `configurationWarnings` and `targetWarnings` and the printed warnings are no longer doubled. Left: the other lists above; the warnings that discovery prints (`registration.ts`, `graph.discovery.warnings`), which every such entry prints; and the targets and named inputs themselves, which Nx merges key by key, so that entries with different options (`targetNames`, `envInputs`, `locked`) give a project a mix of both, decided by the order in which Nx merges them. `DES-PLUGIN-OPTIONS` ("Several entries") settles only the workspace-wide settings of such entries.

- [x] Decide with the maintainer what two entries that receive one workspace mean: only the first entry by its place in `nx.json` creates the project (the others' options do not apply to it), the entries must agree on every option that changes a project, or graph creation refuses such entries
- [x] Record the decision in `DES-PLUGIN-OPTIONS` and implement it, with tests with plugin isolation on and off

## Summary of Changes

The maintainer decided on 15 November 2026: refuse such entries ("Refuse it (Recommended)"; not chosen: "first entry wins", "entries must agree"). Recorded in `DES-PLUGIN-OPTIONS` ("Several entries": each Cargo workspace belongs to one entry; two or more entries that receive manifests of one workspace fail graph creation, naming the workspace, the entries by place with a manifest each receives, and the remedy; fails closed where the plugin cannot tell), in `DES-DIAGNOSTICS` (table row replaced; "Warnings where they are seen" no longer has the first-entry attach rule, only first-entry printing of warnings that name crates of several entries), and in `DES-METADATA-REPORT`, `DES-PROJECT-GRAPH`, `DES-LOCKFILE-HASHING`, `REQ-MULTI-WORKSPACE` and the configuration guide. Verified by `VER-CONFIGURATION`; `VER-GRAPH`, `VER-CARGO-UNCHANGED` and `VER-SETUP` lose the cases of the refused configurations.

Stricter reading taken, to confirm with the maintainer: entries that split one workspace (the root manifest to one, members to another) are refused too, although that configuration was designed and tested before. A manifest that no workspace claims, such as a vendored crate's, can still go to several entries.

Code: `checkEntries` (`entries.ts`) implements the refusal and returns the entry's view; removed as dead: the disagreement check of `testRunner`/`affectedTests`/`featureUnification` and `setInTable`/`workspaceWideSettings`, `entryView` with its options matching, the first-entry attach rule in `projectNodes`, `Registration.attachesWarningsOf`, the first-entry printing in `failOnTargetDefaults`, `workspacesWithoutRootProject` (an unhanded root manifest now goes to no entry) and the own-workspace filters of `otherEntriesWorkspaces`. Kept: `warnsHere` for warnings naming crates of several entries' workspaces.

Tests: refusal for the issue's example with plugin isolation on, off and through the daemon (printed once per failing entry); the same with an `exclude` creates a graph equal to one entry's; near misses (split, one member excluded, an exclude matching nothing, identical entries, three entries, root workspace; passing negated includes and full excludes); fail-closed cases in-process (Nx 24.0.6 itself rejects a string `exclude` first); cross-entry warning printed once. Removed the tests of the refused split and overlap configurations; the end-to-end disagreement test now expects the refusal.

Checks run: `NX_DAEMON=false pnpm nx run-many -t build lint test --skip-nx-cache` (45 suites, 1428 passed, 1 todo), `pnpm nx format:check --all`, `pnpm nx e2e nx-rust-e2e --skip-nx-cache` (27 passed), `mara schema validate`, `mara project validate` (valid, evaluation complete, no errors or warnings), `zban check`.

## Review fix (15 November 2026)

The maintainer confirmed the stricter reading ("Refuse splits too (Recommended)"); `DES-PLUGIN-OPTIONS` says so. The review found that the plugin worked out another entry's files with `findMatchingConfigFiles` alone, while Nx 24.0.6 first globs a narrow `include` natively (`globPluginFiles`, `canGlobInclude`); the plugin then refused entries that Nx keeps apart, such as one with `include` `rust/[[:upper:]]argo.toml`. The plugin now calls Nx's whole choice of an entry's files (`retrieveProjectConfigurationPaths` with the entry alone, then `findMatchingConfigFiles`), and the self-check requires an entry that gets exactly the manifests that Nx handed this one. `EVD-NX-24-ENTRY-CONTEXT` records the pipeline with source lines and the measurement (old recomputation a superset in every case, mirrored one equal in every case, isolation on and off, daemon, a manifest added later); `DES-PLUGIN-OPTIONS` states the superset direction for any approximation and why, and that the old self-check could not misfire; `VER-CONFIGURATION` has the regression cases, tested with isolation on and off. Checks after the fix, on the final head: `NX_DAEMON=false pnpm nx run-many -t build lint test --skip-nx-cache` (45 suites, 1432 passed, 1 todo), `pnpm nx format:check --all`, `pnpm nx e2e nx-rust-e2e --skip-nx-cache` (27 passed), `mara schema validate`, `mara project validate` (valid, evaluation complete, no errors or warnings), `zban check`.
