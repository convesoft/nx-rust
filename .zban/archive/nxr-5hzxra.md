Goal: a cached task that depends on a crate's `build` and reads its executable never stores a result made from the executable of `cargo test` (`GOAL-TRUSTED-CACHE`). The maintainer decided how (below).

Context: found while working on nxr-yfh7zh (`EVD-BATCH-FILES-ON-DISK`, fourth row of its table). In the `binary-tests` fixture, `cargo test` links `app` with the feature `extra` that its dev-dependency turns on, while `cargo build` leaves it off. A cached JS target `pack`, with `app` as an implicit dependency, the inputs `["default", "^default"]`, `dependsOn` on `app:build` (and on `app:test`, to fix the order) and the command `mkdir -p dist && ./rust/target/debug/app > dist/out.txt`, stores `extra` in `nx run-many -t build test pack -p app pack` with batching on (batching off was not run): Nx stores `app:build` before the `test` batch, the `test` batch links `app` again, and `pack` runs after it, so that a later `nx run pack:pack` would restore `extra` beside a restored `app` that prints `plain`, as in the build case of nxr-yfh7zh. With `dependsOn` on `app:build` only, whether `pack` runs before or after the `test` batch is up to Nx's order. The `build` entries themselves are right.

nxr-yfh7zh made each group of `build`, `napi-build` and `wasm-build` keep the files of the command's other cached builds and put them back after its commands (`DES-BATCH`, "Files that a batch leaves on disk"). The same mechanism applied to `test` and `bench` groups fixes this case: it was tried, `pack` stored `plain`. But afterwards the artifact directory holds the executable of `cargo build`, not of `cargo test`. That contradicts what the maintainer accepted with `ADR-TEST-AFTER-BUILD` on 14 November 2026 ("after a command that runs both, the artifact directory holds what cargo wrote last, the executable of `cargo test`, as plain `cargo build && cargo test` leaves it, while the cache entries are right"), and `VER-CARGO-UNCHANGED` and `VER-BATCHING` check it (9 tests in `batch-runs.spec.ts` and `test-after-build.spec.ts` failed with it). So it was not done.

Options for the maintainer:
1. Recommended: `test` and `bench` groups of a batch keep the files of the command's cached builds too. After a batched command, the artifact directory then holds what `build` stored, not what `cargo test` wrote. Change `ADR-TEST-AFTER-BUILD`'s accepted consequence, `RISK-ARTIFACT-DIR-WRITERS` ("The files after a run"), `VER-CARGO-UNCHANGED` and the tests that check it. It costs a hard link per file and group. With batching off the case remains (nxr-fpc72j).
2. Keep the files as they are and record the limit in `RISK-ARTIFACT-DIR-WRITERS`. Users then have to make such a task depend on nothing that runs `cargo test`, or not cache it.

- [x] Ask the maintainer which option
- [x] Implement it, with the check in `VER-BATCHING`

## Decision of the maintainer (20 November 2026)

Asked what should happen for tests, he chose "Put builds' files back (Recommended)". A `test` or `bench` batch keeps the executables of the command's cached builds and puts them back when it ends, so that after a batched command the artifact directory holds what `build` stored, not what `cargo test` wrote; this changes the consequence he accepted with `ADR-TEST-AFTER-BUILD`. A task that reads the file while the tests run can still get `cargo test`'s; that stays a stated limit, as does batching off. Not chosen: failing such test tasks, stating the limit only.

`ADR-TEST-AFTER-BUILD` records the answer (nxr-yfh7zh, phase 1). Still to change with the implementation: `RISK-ARTIFACT-DIR-WRITERS` ("The files after a run"), `VER-CARGO-UNCHANGED` (the artifact directory after `nx run-many -t build test`), `VER-BATCHING` and `DES-BATCH` ("Files that a batch leaves on disk"), and the tests that check the old consequence (`batch-runs.spec.ts`, `test-after-build.spec.ts`). `nx-rust/src/executors/kept-files.ts` and its spec, from commit 41c2299 of nxr-yfh7zh, are the mechanism: change `linkingTargets` to `test` and `bench` and call it from their groups. Its review at d0971e5 found that a glob output is not kept (`keptOutputs` takes the declared output as a literal path), and that a task reading the file while the tests run can still get the test build; the first needs fixing here, and the second is the stated limit.

Note from nxr-yfh7zh (20 November 2026): a `build` whose outputs are explicitly empty declares nothing for a `test` batch to keep. Decide here whether such a build's files are kept too (nxr-j55xdy, closed for builds).

## Summary of Changes

Each `test` and `bench` group of a batch keeps the final files of the command's cached builds that its cargo commands can link again in a stage of the artifact directory, and puts back those that the commands replaced or removed when it ends, so that after a batched command the artifact directory holds what `build` stored (`DES-BATCH`, "Files that a test batch puts back"). Where a file cannot be looked at, kept or put back, or the kept file was written in place or had its permissions changed, every task of the group fails with the message of `DES-DIAGNOSTICS`.

After the review of c08c014 the design changed (decisions A and B below). The candidates come from the crates the group can relink (`workspaceMembers` or each member's `package` of `groupInvocations`, filtered by `testReplacesExecutables` for `test` and by having a binary for `bench`), their final file names (`finalFileNames`, now shared with `targetOutputs` in `nx-rust/src/graph/outputs.ts`), the group's triples (`callTriples`) and profile folder (`profileFolder`) from `build-records.ts`, and the physical artifact directory from `reportedDirectories`: one `cargo metadata --no-deps` per test group wherever the command has a cached `build` that the group may keep files of, with an output inside the repository, and a crate of the group can link files again, also where that build's outputs then name no candidate. A candidate is kept where a cached `build` task (`cache === true`) stores it through one of its resolved outputs: the path, a folder above it, or a glob or exclusion that Nx's `matchGlobPaths` accepts for that one path (each output also with `/**`). Absolute outputs inside the repository are made relative, others ignored. No folder is walked. The kept files live in a stage (`createStage`, `pathInStage`, `moveStagedFiles`, `removeStage` in `stage.ts`); `stage.ts` gained only `pathInStage` and doc comments. In `binary-tests` a whole-workspace test group now keeps `debug/app`, `debug/benched` and `debug/harnessless` (3 files; `gated`'s binary is never built).

Knowledge: `DES-BATCH` ("Files that a test batch puts back" rewritten, the guarantee sentence scoped to builds, "Staged builds" names the second use), `ADR-STAGED-BUILDS` (second use), `ADR-TEST-AFTER-BUILD`, `RISK-ARTIFACT-DIR-WRITERS`, `DES-OUTPUTS`, the user guide in `caching.mara.md`, the `DES-DIAGNOSTICS` row, `VER-CARGO-UNCHANGED`, `VER-BATCHING`, `EVD-BATCH-FILES-ON-DISK` and `EVD-NX-24-BATCHES` (scoped to the implementation measured).

Tests: `kept-files.spec.ts` checks the candidates (scopes, bench, triple and profile, every final file kind, file, folder, glob, exclusion, absolute path, `cache: false`, empty outputs, outside the repository, link above, no directory report without a cached build, matcher and report failures) and the stage (replaced, removed, untouched, missing, folder, link, write in place, permission change, cannot look at, cannot keep, cannot put back, a stage left by an ended process removed by the next keeping). `test-after-build.spec.ts` has the real-tools `pack` case (the executable is deleted too before the restore) and the two failure cases, which now assert that every `test` task of the group fails. `batch-runs.spec.ts` expects `plain` batched and `extra` with `--batch=false`.

## Decisions made

- A (orchestrator, after the review and a second opinion): a group keeps the final files of the crates its commands can relink that a cached `build` of the command stores, judged from the outputs and `cache` flag Nx resolved, instead of expanding outputs into files, which re-implemented Nx. Under a widened output only final files are put back; a glob with an exclusion can keep a file Nx would not store; an output spelled through a symbolic link above the file does not name it (`DES-BATCH`).
- A: a `build` with `cache` off, or with empty outputs, keeps nothing, since Nx stores nothing for it (`DES-BATCH`).
- A: a kept file whose permissions changed counts as changed in place (`DES-BATCH`, `DES-DIAGNOSTICS`).
- B (orchestrator): the kept files live in a stage of the artifact directory, so that a batch killed mid-group leaves only a stage, removed by the next staged command or test group, and no inferred output names a kept file (an output widened to the whole artifact directory also stores a left stage until then, a stated limit); the artifact directory then holds the test build until the next `build` (`DES-BATCH`, `ADR-STAGED-BUILDS`). This closes nxr-nbdazw.
- A test group asks cargo for its directories once wherever the command has a cached `build` it may keep files of with an output inside the repository and one of its crates can link files again (`DES-BATCH`): `task.ts` is off limits and the group's report of the members does not carry the artifact directory.
