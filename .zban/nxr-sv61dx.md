Goal: the maintainer reads, once, the decisions that the control plane made on his behalf while milestone 0.3 (nextest, affected tests and the coverage baseline) was built, and overturns those he disagrees with. A decision he overturns becomes a new issue. This issue is never dispatched to a worker.

Each line says what was decided, which Mara items it rests on, and how to undo it. "Provisional" marks a decision of a kind the maintainer reserved for himself that can still be undone and was therefore taken without stopping the work.

- [ ] Read the list below and overturn what is wrong

## Decisions

1. The three spikes of 0.3 (nxr-hvw1rq and nxr-3qe5zj on `RISK-CARGO-AFFECTED`, nxr-3k3z1j on `RISK-COVERAGE-COST`) were started on 16 November 2026, before the 0.2 epic closed. They measure cargo-affected, nextest and coverage collection on a real workspace and change no code that 0.2 touches; only the features of 0.3 need the batch executor. Rests on the goal that the plugin becomes usable sooner; the order of the epics stays for everything that builds on 0.2. Nothing to undo: the spikes end in evidence items.

From the spikes on cargo-affected (nxr-hvw1rq and nxr-3qe5zj, 16 November 2026; evidence `EVD-CARGO-AFFECTED-REPORT` and `EVD-CARGO-AFFECTED-COST`). Both assumptions of `RISK-CARGO-AFFECTED` hold, with the conditions that these decisions set. All of them are in `DES-TEST-RUN` steps 1 to 4 unless another item is named.

2. The selection is passed in `-E` arguments (at most 64 KiB each, whole binaries above 512 KiB in all, no nextest run for an empty selection), not through a configuration file, because the repository's nextest `default-filter` overrides a tool configuration's. Rests on `REQ-CARGO-UNCHANGED`. Undo: step 3.
3. cargo-affected runs with git's `diff.relative`, since without it a workspace below the top of its git repository (the usual Nx layout) selects nothing and warns of nothing; and the plugin checks the report against git's own list of changed files (every collection the report rests on and the working tree, both ends of a rename, deletions, untracked files; a changed submodule or a declared input that git ignores runs the full suite). Rests on `GOAL-TRUSTED-CACHE`. Undo: step 1.
4. A report is used only when cargo-affected exits 0 with `schema_version` 1 and `hit-exact` or `hit-with-divergence`; anything else runs the full suite and the task says why. Undo: step 1.
5. The mode command reads the coverage database read-only and never starts `status`, which would build the tests at hashing time; it prints `full` when it cannot read it (`DES-TEST-MODE`). Undo: that sentence.
6. Coverage narrows only a Rust file with coverage rows, in a member that is no proc macro, that is not a build script and that no `fileInputs` names. Everything else widens by what the file is: proc-macro sources, build scripts, declared files, non-Rust files and files without rows add all tests of their crate and of every crate that depends on it; toolchain and Cargo configuration files add the whole group (`ADR-AFFECTED-TESTS-WIDENING`, from `REQ-SELECTION-SAFETY`). The review showed that a file with coverage rows of its own, such as a proc-macro crate with unit tests, would otherwise select only its own tests. Undo: step 2.
7. Whose a changed file is comes from the tasks' declared inputs across the whole repository, not from the workspace folder: shared files beside the crates and path crates elsewhere count for every crate whose `test` inputs hold them; a file that no crate of the group has as an input adds nothing; a file the plugin cannot place runs the full suite. Undo: step 2.
8. Programs started by tests: a crate with a binary target runs all its integration tests in affected mode, and every crate that depends on it (a cargo dependency of any kind, an Nx dependency, or declared inputs that reach its folder) runs all its tests when it changes. A test that starts a program without any declared relation is outside what the plugin can see. Undo: step 2.
9. A baseline is trusted only in the context it was collected in: features, profile, target triple and hashes of the declared environment inputs are recorded beside it, and a difference or a missing record runs the full suite (`ADR-AFFECTED-BASELINE-CONTEXT`, `DES-BASELINE`). cargo-affected's own fingerprint does not hold them. Undo: stop writing and comparing the record.
10. Provisional (it is a known way for an affected run to skip a failing test). Two limits stay and are stated in the user guide beside the sentence that an affected run never stands in for the full run: code that another crate evaluates at compile time (a `const fn` used in a `const`, a macro by example) leaves no coverage row for that consumer; and a build script that reads Rust source of its own crate is seen only if that file is declared in `fileInputs`. Closing either would mean widening every library change to all tests of all dependents, or every Rust file of a crate with a build script, which ends the narrowing. Rests on `RISK-CARGO-AFFECTED` (possible, major; the feature is off by default and a subset result never satisfies the full mode's key, `REQ-TEST-MODE-KEY`). Undo: take the wider rule in step 2.
11. Waiting on the maintainer, nothing depends on it: whether to report to the cargo-affected project that a workspace below the top of its git repository selects nothing without `diff.relative` (it leaves the repository; backlog issue nxr-4bhgkd).

12. The implementation issues of 0.3 that build only on the batch executor and the test steps of `workspace-build` (nxr-jb6g5y, the nextest runner, first) were started on 16 November 2026, once nxr-8f9dz2 was merged and before the 0.2 epic closed; what is left in 0.2 (the `hakari` and `cargo` strategies) does not touch them. Rests on the goal that the plugin becomes usable sooner. Nothing to undo.

From the spike on the cost of coverage collection (nxr-3k3z1j, 16 November 2026; evidence `EVD-COVERAGE-COLLECT-COST`: cheap on ripgrep, far too expensive on rust-analyzer, where a full collection took about 650 s against a 31 to 44 s test run and the database grew to 8.75 GB; `RISK-COVERAGE-COST` is now likely for workspaces with many fast tests). All in `DES-BASELINE`.

13. Coverage builds get no build directory of their own by default: instrumented and normal builds did not evict each other in one build directory on Cargo 1.100.0, and the switch for a separate directory stays for CI setups that cache the build directory. Cargo 1.91 could not be measured; if an older Cargo evicts, the cost is rebuilding, never a wrong result. Rests on `REQ-CARGO-UNCHANGED`, `DES-BUILD-DIRS`. Undo: make the switch the default.
14. A full collection starts from an empty database: the target removes `target/affected/coverage.db`, its `-wal` and `-shm` files and the context record itself (collecting over the old database took 957 s against 652 s into an empty one). Undo: stop removing the files.
15. `collect --diff` stays also after a change that re-collects many tests, although it was slower than a fresh full collection there; choosing beforehand would need `status`, which reads the database about as long. Undo: add a rule based on the size of the selection.
16. The context record is removed before every collection, full or `--diff`, and written only after cargo-affected has ended successfully, so that a failed or interrupted collection leaves no record and the next affected run takes the full suite (the review showed that a failed collection in another context would otherwise leave the old record beside new coverage). Rests on `GOAL-TRUSTED-CACHE`, `REQ-SELECTION-SAFETY`, `ADR-AFFECTED-BASELINE-CONTEXT`. Undo: none that is safe.
17. The user guide presents affected tests with a coverage baseline as opt-in and says that slow tests make a workspace a candidate, not a sure gain: the widening rules can select the whole suite, and collection runs every test it re-collects under instrumentation. It gives the commands to measure a few representative changes first. Not measured: the savings after widening, the upkeep of the baseline, moving the database between CI runs.

From the nextest runner (nxr-jb6g5y, merged 16 November 2026; evidence `EVD-NEXTEST-RUNNER-STEPS` and `EVD-NEXTEST-CARGO-FLAGS`, cargo-nextest 0.9.152). All in `DES-TEST-RUN` unless another item is named.

18. A group of one crate (such as a crate whose own options set a feature set) runs that crate's plain commands, `cargo nextest run --no-tests=pass -p <spec>` and `cargo test -p <spec> --doc`, without the plugin's tool configuration, and each passes on exit 0. Rests on `DES-BATCH` "Groups of one crate" and `REQ-DOCTESTS` (a result means the same with either runner; nextest exits 4 for a crate without tests unless the flag is given). Undo: drop the flag, or use the nextest step for one crate.
19. A test runner that the user configured in Cargo does not split a nextest group, because nextest starts no runner of the plugin's. Undo: apply the configured-runner check of the cargo runner to nextest too.
20. The package filterset is split into `-E` arguments of at most 64 KiB, as step 3 already requires for the selection. Nothing to undo.
21. Provisional (it touches the separate build and run phases that `ADR-SINGLE-MACHINE` names; marked in `DES-TEST-PHASES`). With nextest, one `cargo nextest run` holds both build and run, and the executor keeps them apart in its reading (exit 101 against the report). A separate `cargo nextest run --no-run` would contradict the two commands per group of `DES-TEST-RUN` and `VER-TESTING`. Undo: add that command as a build step.
22. The JUnit reading counts a `failure` or `error` element as failed, `flakyFailure` and `rerunFailure` as tries and a `skipped` element as not run, and treats every contradiction between report and exit status as failed. Rests on `GOAL-TRUSTED-CACHE`. Undo: none that is safe.
23. From the review: after exit status 100 (a failed test or a run that ended early, such as a global timeout, which leaves no trace of the tests that never ran) the expected tests come from `cargo nextest list --message-format json`; a task passes only where every test of its package that the list names ran and passed. The alternatives were nextest's line for people and its experimental libtest-json output. The list runs only after 100, so a passing group keeps two commands. Rests on `GOAL-TRUSTED-CACHE`. Undo: take another source of the expected tests.
24. From the review: nextest's version (or that it is missing) is part of the key of a test that runs with nextest, and of no other key. Rests on `GOAL-TRUSTED-CACHE`, `DES-INPUTS`. Undo: drop the line from the toolchain command.
25. From the review: an unknown kind of suite in the report fails every task of the group, a `@stress-<n>` suffix is stripped, and a failed setup script fails every task and is named. Groups that select crates with `-p` under the `hakari` and `cargo` strategies get the nextest step with only their own commands. Undo: the suite reading in `nextest.ts`.

From the test mode input (nxr-539qtw, merged 16 November 2026; evidence `EVD-TEST-MODE-READING`). All in `DES-TEST-MODE`, with the "Test mode" row of `DES-INPUTS`.

26. From the review: the mode command never opens cargo-affected's database in a way that can write. It reads only through an immutable, read-only open and prints `full` wherever it cannot be sure it read the whole, settled database: a `-wal` file before or after the read, a database file that changed in between, or a failed read. So a baseline whose collection is running or was interrupted gives the full suite until a collection has closed it cleanly; the testing guide says so. Rests on `DES-TEST-MODE` ("without writing to it"), `REQ-CARGO-UNCHANGED` in spirit and `GOAL-TRUSTED-CACHE`. Undo: read through an ordinary read-only connection where a `-wal` file exists and accept the leftover `-wal` and `-shm` files.
27. The command takes the commits of every fingerprint in the database, not only the current one, because finding the current fingerprint would mean hashing what cargo-affected hashes; an extra commit only splits keys. Rests on `GOAL-TRUSTED-CACHE`, `EVD-CARGO-AFFECTED-COST`. Undo: narrow to the current fingerprint.
28. An invalid value of `NX_RUST_TEST_MODE`, the empty value included, fails the task before cargo runs and prints a key line of its own, so that a failure stored with `NX_CACHE_FAILURES=true` never serves a valid mode. Undo: count the empty value as not set.
29. CI detection is a copy of Nx 24.0.6's `isCI`, compared with the installed Nx in a test, because loading Nx inside the command would cost more than the rest of it (about 18 ms of Node start plus about 40 ms of query on a 200 MB database). Undo: load Nx's own function.
30. The input is on the `test` of every crate of a selecting workspace, also one that opts out with `affectedTests = false`; such a crate runs its full suite under a key per mode, which is safe. Undo: leave the input out for crates that opt out.
31. Accepted for this issue: the command is not checked against a database written by a real cargo-affected (producing one needs the `llvm-tools` component, which the machine lacks); the test databases follow the schema in cargo-affected 0.4.1's source. A wrong reading can give `full` or a split key, never a result restored under a key it does not satisfy. nxr-tabkjx, which runs the real tool, adds the real-database case. Also stated in the guide: a Node without built-in SQLite (before 22.13) always gets `full`.
32. Not fixed here, carried into nxr-tabkjx: the executor reads the baseline again for itself, so a collection that creates or changes the baseline between hashing and the run can give the executor another mode than the key holds (`RISK-SUBSET-AS-FULL`). Today both modes run the full suite; nxr-tabkjx must guard it before it selects tests.

From the selection of affected tests (nxr-tabkjx, merged 17 November 2026; evidence `EVD-TEST-MODE-GUARD`, cargo-affected 0.4.1). In `DES-TEST-RUN` unless another item is named.

33. The guard between hashing and the run (`DES-TEST-MODE`, "Between hashing and the run"). Nx 24 hands an executor no hash details and hashes some batch tasks again after they ran, so the mode command records what it prints for each `nx` command under `.nx/workspace-data/nx-rust/test-mode`, with a command id from the plugin's `preTasksExecution` hook; a subset run is recorded before it starts, after which another value in the same command prints a value that is never restored; the executor also checks that cargo-affected's report rests only on commits it read at the start; `postTasksExecution` removes the record. Rests on `REQ-TEST-MODE-KEY`, `GOAL-TRUSTED-CACHE`, `RISK-SUBSET-AS-FULL`. Not taken: comparing the database files' times (`cargo affected status` writes the database on every run) and recomputing the key in the executor. Undo: none that is safe.
34. From the review: no evaluation is set aside. A task selects only where every mode that its `nx` command recorded for its workspace, `full` included, equals the mode its executor reads; otherwise it runs the full suite and says the command's tasks were hashed in different modes. The review showed a subset stored under a `full` key where one crate's `.env.test` changed between hashing and the run. The rule cannot be narrowed to the task's own evaluation, because Nx runs a runtime input in an environment that names no task. Cost: a command whose tasks of one workspace ask for different modes runs all of them in full. Undo: none that is safe.
35. Form of the context record (`DES-BASELINE`, `ADR-AFFECTED-BASELINE-CONTEXT`): JSON at `target/affected/nx-rust-context.json` with the fields `cargo`, `triple`, `env` and `runtime`; the variables are those Nx expands for the test tasks plus the `CARGO_PROFILE_`, `CARGO_TARGET_` (not `CARGO_TARGET_DIR`) and `NEXTEST_` ones. Undo: change the form in `baseline-context.ts` and `DES-BASELINE`.
36. From the review: the context record (version 2) also holds a hash of the output of every runtime input of the `test` tasks except the test mode command, the declared `runtimeInputs` and the plugin's own such as the toolchain; the executor evaluates them again at the run, and a different output, a failing command or a record of version 1 runs the full suite and names the input. The review showed that a file outside the repository, read through a declared runtime input, could change without any test being selected. Extends `ADR-AFFECTED-BASELINE-CONTEXT`; rests on `REQ-SELECTION-SAFETY`. Undo: drop the field, which leaves a change outside git unseen.
37. Every input of the group's tests that git ignores, and every input outside the git repository, runs the full suite, not only declared ones. The review checked that an ignored root `.env`, Cargo's build directories, the lockfile digests and the napi and wasm outputs are no such inputs, so a common setup does not fall back because of this. Rests on `GOAL-TRUSTED-CACHE`. Undo: backlog issue nxr-rsdjab, which narrows the check to declared files.
38. Placing changed files (step 2): an existing file by the file lists of Nx's own hash plan inspection, under the configured name of the test target; a deleted path or the old path of a rename by Nx's input expansion and glob matcher, trusted only where that reproduces the inspection's lists; a path at the repository root counts for every crate; otherwise the full suite. From the review: an inspection that throws runs the full suite, and a renamed test target (`targetNames`) works. Undo: run the full suite for every path that no longer exists.
39. In the binary rule of `ADR-AFFECTED-TESTS-WIDENING`, "a declared input that reaches the binary crate's folder" means any test input below that folder except its `Cargo.toml`, which every crate's test holds. Undo: drop the exception, which makes every crate a dependent of every binary crate.
40. The `-E` arguments (step 3) are `(packages of their parts) & (parts)`; a binary crate's integration tests are `package(=<name>) & kind(test)`; a single task in affected mode runs through the group path and prints its output when its steps end. Undo: in `affected.ts`, `targets.ts` and `runTask`.
41. From the review: the hooks never fail an `nx` command. Removing the guard's record is best effort, and where the record cannot be written or read, tasks in affected mode run the full suite and say why. Nothing to undo.
42. In the tests, `llvm-cov` and `llvm-profdata` come only from the toolchain the tests run with or from the folder a test variable names, with the toolchain's LLVM version; otherwise the real-coverage cases skip with a warning. So these cases ran on Cargo 1.100.0 and not on 1.91.0, for which the machine has no matching tools. Test harness only.
43. Two issues went to the backlog: nxr-4byqv8 (a task that Nx hashes while another task's `cargo affected status` runs gets the full suite) and nxr-rsdjab (line 37). Not run: macOS and the Nx daemon. Undo: pull an issue back.
