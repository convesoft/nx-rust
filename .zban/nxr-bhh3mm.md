Goal: the maintainer reads, once, the decisions that the control plane made on his behalf while milestone 0.4 (napi and wasm artifacts) was built, and overturns those he disagrees with. A decision he overturns becomes a new issue. This issue is never dispatched to a worker.

Each line says what was decided, which Mara items it rests on, and how to undo it. "Provisional" marks a decision of a kind the maintainer reserved for himself that can still be undone and was therefore taken without stopping the work.

- [ ] Read the list below and overturn what is wrong

## Decisions

1. The spike nxr-v3y6cr (`RISK-NAPI-TOOLING`: whether the napi CLI can post-process an existing cargo build) was started on 16 November 2026, before the 0.2 epic closed. It tries the napi CLI on a small crate and changes no code that 0.2 touches. Rests on the goal that the plugin becomes usable sooner; the order of the epics stays for everything that builds on 0.2. Nothing to undo: the spike ends in an evidence item.

2. From the napi spike (nxr-v3y6cr, 16 November 2026; evidence `EVD-NAPI-POSTPROCESS`): the napi CLI cannot post-process an existing cargo build, since `napi build` always runs cargo. `napi-build` therefore compiles inside the batch as a group of its own kind, and only that step sets the type-definition variables; the post-processing calls the exported functions of `@napi-rs/cli` (`readNapiConfig`, `generateTypeDef`, `writeJsBinding`), never `napi build`. Rests on `DES-ARTIFACT-STEPS`, `DES-BATCH`, `ADR-WORKSPACE-FEATURES`. Undo: run `napi build` per crate as a group of one crate, or switch back if the CLI gains a mode that skips cargo.
3. A fresh type-definition folder for every napi compile (emptied at the group configuration's path), every napi-derive crate of the addons' dependency closure forced, and every such crate required to write its file; where one writes none, every `napi-build` task that depends on it fails and names the crate and the two causes (its build script does not run `napi_build::setup()`, or it has no `#[napi]` item left). The review reproduced three ways in which a kept folder gave stale or incomplete type definitions. Rests on `GOAL-TRUSTED-CACHE`. Undo: keep files between runs, if napi-rs offers a reliable way to remove stale ones.
4. Two addons whose library has one file name fail in `napi-build` before cargo runs, since cargo builds one file for both. Rests on `DES-OUTPUTS` ("Files of one name"). Undo: copy each crate's own library, if cargo ever builds separate files.
5. Provisional (it touches the need behind `REQ-CARGO-UNCHANGED`). The napi compile shares cargo's build directory (`ADR-NAPI-SHARED-BUILD-DIR`). After `napi-build`, the next plain `cargo build`, `nx build` or rust-analyzer check compiles the napi crates and every crate that depends on them again, and the other way round (measured: well under 0.2 s on a 41-unit workspace). The need and the requirement are unchanged; the decision item states the exception. Chosen over a build directory of its own for the napi compile, which compiles the whole workspace a second time under `workspace-build`; addon crates are usually leaves. Undo: give the napi compile its own build directory, which changes no output and no key.
6. Provisional (it narrows what the target serves). Only napi-rs 3 is supported: `napi-derive` 3 with `@napi-rs/cli` 3.4.0 or later, with a message for anything else (`ADR-NAPI-RS-3`). The previous CLI major exports none of the functions and cannot build napi-derive 3 crates; v3 was announced in July 2025. `REQ-ARTIFACT-TARGETS` names no version and is unchanged. Undo: the backlog issue nxr-w2rbxq (napi-rs 2 crates).
7. Waiting on the maintainer, nothing depends on it yet: `REQ-CARGO-UNCHANGED` says that the plugin generates no files inside crates, while `napi-build` writes the `.node` file, `index.js` and `index.d.ts` into the crate's folder, as napi-rs projects expect. Changing the requirement's wording is the maintainer's; the question is filed as the backlog issue nxr-f87kzs. Until he answers, the design stands as written (outputs in the crate's folder).

From the specification of mixed projects (nxr-ym403k, 16 November 2026; evidence `EVD-NX-MIXED-CONSUMER` and `EVD-NX-PROJECT-MERGE`; `REQ-MIXED-PROJECTS` is accepted). A mixed project is a folder that is both a crate and a JS package. The issue asked to settle these "with the user"; they were decided from Mara and checked against Nx 24.0.6.

8. The project's name is the folder's `project.json` name, else the `package.json`'s; the crate's name and its `name` override do not apply there. Rests on `REQ-PROJECT-NAMES`, `ADR-PROJECT-NAMES`. It is how Nx merges; nothing to undo.
9. The plugin keeps its target names. Where the folder's `package.json` script or `project.json` target, or a plugin listed later, replaces or merges into one, it neither renames nor reports; the guide names `nx.includedScripts`, plugin order or `exclude`, and `targetNames` as the ways to keep cargo's targets (`ADR-MIXED-PROJECT-TARGETS`). Not chosen: automatic renaming, and a warning or error, which would fire on every napi-rs template crate. Rests on `REQ-METADATA-OVERRIDES`, `REQ-TARGET-NAMES` and the guard's rule for other layers. Undo: add a warning later, which breaks nobody.
10. A JS consumer's dependency on the crate enters the project graph through Nx's own analysis of the consumer's `package.json`; the plugin adds no edges to or from JS projects. A crate without a `package.json` goes into the consumer's `implicitDependencies`. Rests on `ADR-NO-RUST-BUILD-DEPS`, `DES-PROJECT-GRAPH`. Undo: let the plugin add edges.
11. The consumer's cache key: `^default` covers the crate's files but not what only the crate's own key holds (lockfile digests, toolchain, variables, tool versions), so by default a JS build can be restored from the cache after the artifact was rebuilt differently (the review reproduced it with `RUSTFLAGS`). The guide tells the user to make the JS target depend on the artifact target and to hash its outputs with a `dependentTasksOutputFiles` input, and warns about the default. Rests on `GOAL-TRUSTED-CACHE`, `ADR-NO-RUST-BUILD-DEPS` (the plugin changes nothing in JS projects). Undo: a generator could write that input.
12. The consumer's `^build` runs the merged project's `build`, whatever replaced it, with that target's own `dependsOn`; a replacing build with a `^build` of its own also runs the native builds of the crates behind it, which costs time, not correctness. Provisional: one sentence was added to the accepted requirement `REQ-NO-RUST-TASK-DEPS` to say so, marked provisional in its text; it qualifies the earlier unconditional wording. Undo: remove the sentence and the paragraphs in `ADR-NO-RUST-BUILD-DEPS` and `DES-TARGETS`.
13. Provisional: one sentence was added to the accepted requirement `REQ-INFERRED-TARGETS`, marked provisional in its text: in a folder that is also a JS project, the folder's files and plugins listed later replace or merge into inferred targets. It restates for targets what `REQ-INFERRED-PROJECTS` already says for the project. Undo: remove the sentence.
14. A root `package.json` script or `project.json` target that replaces the workspace project's `lockfile` target: graph creation reports nothing, the crates' cached tasks fail and store no result, and the guide gives `targetNames` as the fix. The failure's message wrongly blames a changed `Cargo.lock` (backlog issue nxr-fwq2yw). Rests on `GOAL-TRUSTED-CACHE`, `DES-LOCKFILE-HASHING`. Undo: add an error at graph creation.
15. A workspace project whose folder already is an Nx project follows the same rules as a crate's folder. Rests on `EVD-NX-PROJECT-MERGE`.

16. The napi target (nxr-tv3r95) was started on 16 November 2026, once nxr-8f9dz2 was merged and before the 0.2 epic closed; it builds on the batch executor and its groups, not on what is left in 0.2. Rests on the goal that the plugin becomes usable sooner. Nothing to undo.

From the napi target (nxr-tv3r95, merged 16 November 2026; `@napi-rs/cli` 3.10.12, napi 3.16.2). All in `DES-NAPI` unless another item is named.

17. `napi-build` runs the `cargo-outputs` executor, and its compile counts as a `build` group for the files that a batch stores: under `workspace-build` a `build` group and a `napi-build` group of one workspace never run in one batch; under `hakari` and `cargo` the rule is per crate (a `build` and a `napi-build` of one crate never share a batch, those of different crates do). Rests on `DES-BATCH` ("Two batch executors", "Files that a batch stores"). Undo: move it to the `cargo` executor and out of the stored-files rule.
18. Provisional (a capability users see; `ADR-V1-SCOPE`, `DES-PLUGIN-OPTIONS`). `napi-build` takes the options `features`, `allFeatures`, `noDefaultFeatures` and `profile` and the `all-features` configuration, and no `targetTriple`. Marked provisional in `DES-NAPI`. Undo: drop `napi-build` from the option sets.
19. The crates whose type definitions an addon needs come from `cargo tree -e normal` with the compile's selection, feature flags and `--locked`, and under the `cargo` strategy with that strategy's flags, so that the closure is the one the compile builds. Undo: replace the closure lookup.
20. Type definitions go to `<build dir>/nx-rust/napi/<hash>/types`, one folder per task, in the build directory that cargo reports. Undo: change the path.
21. From the review: the library is always the file that cargo's own `compiler-artifact` message of the napi command reports, in groups of one crate as well; no such message, or several for one addon, fails the task. The review showed that copying from the profile's folder stored an older library where `CARGO_BUILD_TARGET` or `build.target` names the host. Rests on `GOAL-TRUSTED-CACHE`. Undo: none that is safe.
22. The outputs' names are set at graph time from `package.json` and the host triple and checked against the installed CLI at run time. Undo: a glob output.
23. The task fails before cargo runs without a `package.json`, on a non-host triple (`ADR-V1-SCOPE`: no cross-compiling of Node addons), without a supported CLI, or on a name mismatch; the CLI is resolved from the crate's folder. `init` counts the CLI as installed only where every crate with `napi-build` resolves one. Undo: the checks in `napi-build.ts`.
24. Groups key on the target as well, since `build` and `napi-build` run the same cargo command and would otherwise share a group. Undo: drop the target from the group key.
25. From the review: the file that `napi.dtsHeaderFile` names is an input of `napi-build`, also where git ignores it, and a header outside the repository, or one that differs from what the graph saw, is refused. Rests on `GOAL-TRUSTED-CACHE`, `DES-INPUTS`. Undo: none that is safe.
26. A cargo-hakari hack crate that depends on `napi-derive` only to unify its features is left out of the crates that must write type definitions; its name reaches the executor through the project metadata. Undo: drop that metadata.
27. From the review: the generated files (`index.js`, `index.d.ts`, the `.node` file) stay inputs of the crate's own npm script targets, which costs reruns and gives no wrong result; the guide states the cost. Undo: nothing to undo.
28. nxr-d5n6zr went to the backlog: the key of `napi-build` holds the version of `@napi-rs/cli`, not the packages the CLI depends on, which a JS lockfile can change without a new CLI version. Undo: pull the issue back.
29. Not run: `napi-build` under the `cargo` strategy, which needs a nightly cargo as every compiling target there; stated in the known limits of the guide.

From the wasm target (nxr-0ap8n4, merged 16 November 2026; evidence `EVD-WASM-POSTPROCESS`, wasm-bindgen 0.2.130). All in `DES-WASM` unless another item is named.

30. Provisional (a capability users see; `DES-PLUGIN-OPTIONS`). `wasm-build` takes the options `features`, `allFeatures`, `noDefaultFeatures` and `profile` and the `all-features` configuration, as `napi-build` does (line 18). Undo: drop `wasm-build` from the option sets.
31. Provisional (a name users type). The JS flavour option is called `jsFlavour` (`web`, `bundler` or `nodejs`), with the default `bundler`, the CLI's own default. Rests on `DES-ARTIFACT-STEPS`. Undo: rename it in the option schema and `graph/wasm.ts`.
32. Provisional (it removes files in the crate's folder). The package is always written to `pkg` in the crate's folder, as wasm-pack does, and the plugin empties that folder on each run; `pkg` is the target's output and is left out of the crate's `default` input. The guide says so, and Nx itself replaces a target's output folder on a cache restore. Rests on `DES-OUTPUTS`. Undo: make the folder an option, or write below the build directory.
33. The CLI is found on the task's `PATH` from the workspace root; its version is compared with every `wasm-bindgen` version that the crate's lockfile entry reaches, and the task fails before cargo on a difference, on a missing CLI or wasm target, on an invalid flavour, and where two crates share a `[lib] name`. The step after cargo fails where the CLI exits successfully without writing the package's `.wasm` file. Rests on `REQ-DIAGNOSTICS`, `ADR-V1-SCOPE` (the plugin installs nothing). Undo: the checks in the wasm executor code.
34. The wasm compile counts as a `build` group of the crates it selects for the files that a batch stores, so a crate's `build` and `wasm-build` never share a batch. Under `workspace-build` each crate gets a compile of its own; under `hakari` one shared `-p` command where `platforms` lists the host and the wasm triple; under `cargo` a shared `-p` command, one per crate with `--features`. Rests on `DES-BATCH`, `ADR-WORKSPACE-FEATURES`. Undo: the selection in `groups.ts`.
35. Corrected on evidence: the build input check read `lib<name>.d`, but for a `cdylib` built for wasm cargo writes `<name>.d`, so the check read nothing for such crates, also for `build --targetTriple wasm32-unknown-unknown`. Point 1 of `DES-BUILD-INPUT-CHECK` now names the right file. Nothing to undo.
36. From the review: the key tells a present `WASM_BINDGEN_ANYREF`, `WASM_BINDGEN_EXTERNREF` or `WASM_BINDGEN_MULTI_VALUE` from an absent one, through the runtime command that prints the CLI's version, because Nx hashes an unset and an empty variable alike while the CLI switches each on by its presence; the CLI's environment is unchanged. Rests on `GOAL-TRUSTED-CACHE`, `DES-INPUTS`. Undo: none that is safe.
37. From the review: the wasm compile builds the library targets only (`--lib`), because a binary of the crate's name would overwrite the library's `.wasm` file (a crate with a wasm library and a command-line binary). `napi-build` was checked and is unchanged: on the host the two do not collide. Undo: drop `--lib`, which brings the CLI's failure back for such crates.
38. Three issues went to the backlog: nxr-pw77kk (a plain `build` for a wasm triple stores no `.wasm` file), nxr-z8cn3b (a wasm crate's dependency file is not counted among the record names that crates share), nxr-27zbta (CI installs none of the optional tools although `verification.mara.md` says it does, so the real-tool cases skip there). Not run: `wasm-build` under the `cargo` strategy with a real cargo (needs nightly), and the real-tool wasm cases on Cargo 1.91.0 (no wasm target installed for it on this machine). Undo: pull an issue back.

## The maintainer's review of the provisional lines (20 November 2026)

- Lines 5, 6, 13, 18, 30 and 32 stand.
- Line 31 is overturned: the option is renamed from `jsFlavour` to `wasmTarget`, with the same values and default (nxr-sy0tsz). It matches `wasm-bindgen --target` as `targetTriple` matches `cargo --target`, and the option schema then has no British-spelled identifier.

The marks of the confirmed lines are removed by nxr-qw96ne.
