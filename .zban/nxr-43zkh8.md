Goal: the maintainer reads, once, the decisions that the control plane made on his behalf while milestone 0.5 (releasing with Nx release) was built, and overturns those he disagrees with. A decision he overturns becomes a new issue. This issue is never dispatched to a worker.

Each line says what was decided, which Mara items it rests on, and how to undo it. "Provisional" marks a decision of a kind the maintainer reserved for himself (anything that cannot be undone, a capability users see) that can still be undone before 1.0 and was therefore taken without stopping the work. Decisions before 15 November 2026, 16:30, are in the Mara items themselves and in the maintainer's own answers; this list starts with the amendments of that day. The maintainer's own answer of 15 November 2026 on uncommitted changes (a documented limit, no check with git; `RISK-UNCOMMITTED-PUBLISH`) is not listed, since it is his.

- [ ] Read the list below and overturn what is wrong

## Decisions

1. A `cargo publish` call runs with its tasks' environment without Nx's per-task variables, and tasks whose environments otherwise differ get separate calls (settled by the worker of nxr-m8evx2, accepted at integration). Rests on `DES-RELEASE` ("Batch") and the rule of `DES-BATCH` that a group has one environment. Undo: one call per task.
2. In a dry run, "another task would publish this dependency" means that the dependency's project has the publish target and its task did not fail (worker, accepted). Rests on `DES-RELEASE` (the dry run's limit). Undo: require the dependency's task to be in the same call.
3. A lookup that did not find a version is asked again before each later call (worker, accepted). Rests on `DES-RELEASE` ("Lookups"): an earlier call of the same run may have published it. Undo: ask once per run.
4. Each task's result comes from what cargo's output shows for its own crate, whatever the call's exit status: `Uploaded <name> v<version>` in a real call, the crate's `Verifying` block reaching `Finished` in a dry run; what the output does not show counts as failed, with a message that says so (review fix). Rests on `DES-RELEASE` ("Batch") and the cargo executors' rule in `DES-BATCH`. Undo: results from the exit status alone, which fails crates that cargo did verify.
5. Three cases of `VER-RELEASE` were reworded to what cargo does: the alias case (cargo always showed `alpha` and refused the upload because two names pointed to one index), the `shared` case (it needs a registry that nothing names), and the missing `registry` key case ("no upload of it": the dependency in the same call still publishes). Rests on `EVD-CARGO-PUBLISH-REGISTRIES` and the runs of nxr-m8evx2. Undo: restore the earlier wording, which the harness could not produce.
6. Provisional (an upload cannot be taken back). nxr-4884vg went to the backlog: the check of where a dependency points uses the dependent crate's environment. With per-crate dotenv files that give the crates of one release different default registries, a crate was uploaded to one registry against another registry's copy of its dependency, both tasks passing (harness only). The release guide says that the crates of one release must get their registry settings from one place. Rests on the rule that rare `.env` variants do not block. Undo: pull the issue back; the fix is to establish each dependency's registry with that dependency's own task environment.
7. nxr-ma1z22 went to the backlog: a `project.json` that sets `"cache": true` on `nx-release-publish` makes a second run report success from the cache without an upload; the release guide says not to turn caching on for that target. Nothing wrong is uploaded. Undo: pull the issue back; the fix is the run-time check that the other uncached targets have.
8. nxr-c63t0r went to the backlog: the publish executor does not run the dotenv check that the cargo executors run. Undo: pull the issue back.

From nxr-k4c6ek (merged 16 November 2026; evidence `EVD-HAKARI-PUBLISHING`, cargo-hakari 0.9.39). All in `DES-RELEASE`.

9. A cargo-hakari hack crate is recognised from the cargo-hakari configuration whatever feature-unification strategy the workspace uses, and gets no `nx-release-publish` target. A configuration that does not parse, or that names no member, gives no hack crate; such a hack crate keeps the target unless it sets `publish = false`. Rests on `EVD-HAKARI-PUBLISHING` (cargo-hakari writes the hack crate with `publish = false`). Undo: take the hack crate from the `hakari` strategy only.
10. Where the check for unpublished dependencies fails for a dependency on the hack crate, the message adds cargo-hakari's two documented ways, also where the hack crate has a `publish` list without the registry; a stub hack crate that is not in the registry yet gets a message of its own, which says to publish the stub once outside Nx. Rests on `DES-DIAGNOSTICS` (a message says what the user can do). Undo: narrow it in the message code.
11. The remedy "change the entry's `registry` key" is offered only where the dependency has a `publish` list, because no registry accepts a crate with `publish = false`. Nothing to undo.
12. An entry that points to a registry other than crates.io whose name the plugin cannot read fails the crate: unknown means fail. Rests on `GOAL-TRUSTED-CACHE` in spirit and on the rule that an upload cannot be taken back. Undo: let cargo decide.
13. The check runs after the crate's own lookup of whether its version is already in the registry (a crate already published is skipped as before); that lookup uploads nothing. Undo: move the check before the lookup.
14. nxr-2mjeq7 went to the backlog: under cargo-hakari's dep-format 1 the dependency on the hack crate has no version, so cargo itself refuses the crate with its own message and the plugin adds no cargo-hakari guidance. Nothing wrong is uploaded. Undo: pull the issue back.

## The maintainer's review of the provisional lines (20 November 2026)

- Line 6 is overturned: nxr-4884vg is pulled back from the backlog and fixed, because an upload to a registry cannot be undone. Each dependency's target registry is established in its own environment, or the release fails early where its tasks disagree on their registry settings.

From the fix that the maintainer ordered for line 6 (nxr-4884vg, merged 20 November 2026 as 36eee81). In `DES-RELEASE` ("A dependency's environment", "Checks before the first call") unless another item is named.

15. A dependency's registry and the lookup of its version use the environment of the dependency's own publish task. The check that a dependency entry points to the registry the dependency really goes to runs for every crate of the run before the first `cargo publish`, and a failure fails every task that the executor received, not only the crates involved. Two existing cases that used to upload the rest of the run now upload nothing: an entry without a `registry` key on a dependency published to another registry, and a registry name configured differently in two Cargo workspaces. Rests on the maintainer's direction and `GOAL-TRUSTED-CACHE`'s rule of erring to the safe side. Undo: fail only the crates involved.
16. For a dependency task that the executor does not run itself (without a batch, or in another release group), the plugin compares the dotenv files that Nx loads for both tasks, by their values before expansion. Cargo settings are the names that start with `CARGO` or `RUSTUP_`, plus `HOME` and `PATH`; tokens and credential providers do not count. Where they differ, the registry counts as not established and the run stops. This refuses some valid setups: without a batch, linked crates whose dotenv files differ in a Cargo setting stop the release even where the settings would agree, and a variable set on the command line is not seen by the comparison (the review confirmed that this leads to a refusal, never to a wrong upload). Undo: narrow the list of settings, or evaluate the files as Nx does.
17. From the review: a dependency published outside the current task graph (an earlier release group, or another command) gets the configuration that Nx's own rule resolves, through Nx's private `ProcessTasks.prototype.resolveConfiguration`, and its registry counts as established only where every configuration that its target declares, and none, give the same Cargo settings. The review had uploaded a crate against the wrong copy of its dependency where the dependency's default configuration had a dotenv file of its own. Rests on the same direction. Nothing to undo; the private function is one more for nxr-gtxq18.
18. Provisional (it narrows what the maintainer asked for, and `REQ-RELEASE` says so now). The check covers one release group at a time: Nx publishes the groups one after another, so a group published earlier stays published, each crate where its own settings sent it, when a later group is refused. No crate is uploaded to a wrong registry or against a wrong copy, but the release is then half done. The guide, `REQ-RELEASE` and `DES-RELEASE` state this boundary. Undo: check the publish tasks of every release group before the first group uploads, which needs the plugin to read the release configuration ahead of Nx.
