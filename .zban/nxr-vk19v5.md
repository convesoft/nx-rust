Goal: the maintainer reads, once, the decisions that the control plane made on his behalf while milestone 0.6 (architecture cleanup and hardening, nxr-e2z8sz) was built, and overturns those he disagrees with. A decision he overturns becomes a new issue. This issue is never dispatched to a worker.

Each line says what was decided, which Mara items it rests on, and how to undo it. "Provisional" marks a decision of a kind the maintainer reserved for himself (anything that cannot be undone, a capability users see) that can still be undone before 1.0 and was therefore taken without stopping the work.

- [ ] Read the list below and overturn what is wrong

## Decisions

1. Every private `nx/src/*` load goes through `nx-rust/src/compatibility/nx-bridge.ts`, which uses the plugin's own peer `nx` only where the repository has no `nx` package at all: a private module missing from the repository's Nx is an error, never a reason to load the peer's, and a resolution error other than a missing module is reported as it is (worker of nxr-gtxq18, accepted at integration). Rests on `REQ-COMPATIBILITY` and `RISK-UPSTREAM-CHANGES`. Undo: fall back to the peer in `resolveFromRepository`.
2. Three differences on failure paths that only a damaged Nx installation reaches were accepted with the bridge: without `matchGlobPaths` the conservative local matcher is used instead of the peer's native one, without `getInputs` one workspace glob is skipped for a deleted path, and a `yargs-parser` without a function fails with the bridge's error instead of a `TypeError` (review of nxr-gtxq18, dropped as exotic by the control plane). Rests on `REQ-COMPATIBILITY` (only an intact, supported Nx counts). Undo: restore each caller's own fallback.
3. The plugin's own specifier lookups (`entries.ts`, `target-defaults.ts`, `plugin-package.ts`) still resolve from the repository root without `.nx/installation`; left to the backlog as nxr-j04frm, since it needs the plugin registered under two specifiers in an `installation` layout (control plane). Rests on `DES-DISCOVERY`. Undo: start nxr-j04frm.
4. Which `cargo metadata` requests wait for one another is judged from manifests alone, without running cargo and without matching `members` or `exclude`: a manifest with a workspace pointer or one that does not parse waits for every request in flight, also where the pointer is in a manifest above one that has no `[workspace]` table (worker of nxr-gp1awx; the ancestor rule decided by the control plane after the review). The set is a superset of what cargo picks, so the only error is an unneeded wait. Rests on `DES-METADATA-REPORT` and `GOAL-TRUSTED-CACHE`. Undo: wait for every request in flight again, in `ComputationReports`.
5. A crate inside `CARGO_HOME` that a workspace around it lists as a member still gets that workspace's report, as before 0.6; left to the backlog as nxr-tbb876 (control plane, exotic). Rests on `DES-METADATA-REPORT`. Undo: start nxr-tbb876.
6. nxr-qkxcmm (the dotenv check) was ordered after nxr-4sr6hd (batch environments without changing `process.env`), because both rework how a batch expands dotenv files and the check depends on how the environment is built (control plane). Rests on `DES-BATCH`. Undo: none needed; an ordering only.
7. The plugin keeps telling its `nx.json` entries apart by the copy of its module that Nx makes for each entry, and adds no fallback keyed by workspace root, name or options: nothing else that Nx 24 passes through the public plugin API differs between entries (worker of nxr-hjpc99, accepted at integration). Where a later hook is not called on its entry's copy, or gets an options object other than the one its `createNodes` received (the same object, not an equal one), graph creation fails with a message instead of answering from another entry. A later Nx that passes a fresh copy of the options to each call would fail every graph until supported, which the end-to-end suite would show first. Rests on `DES-DISCOVERY` ("Entries"), `EVD-NX-24-PLUGIN-ENTRIES`, `GOAL-TRUSTED-CACHE` and `REQ-COMPATIBILITY`. Undo: compare options by value, or drop the checks in `Registration.forHook`.
8. A guard against two `createNodes` calls of one entry in one graph computation was removed again after the review (control plane): Nx's daemon can overlap computations, and a delayed plugin worker then made a valid `nx show project` fail. Overlapping computations of one entry answer from the entry's newest call, as before 0.6. Rests on `EVD-NX-24-PLUGIN-ENTRIES` and `DES-DISCOVERY`. Undo: none advised; the guard depended on Nx's scheduling.
9. Three cases stay undetected and are named in `DES-DISCOVERY`: a copy shared by entries with the same options object or without options, an entry's manifests split between calls of one computation, and one copy's later hook called as a method of another entry's copy with the same options. Nx 24 does none of them (control plane, exotic). Undo: none; the public API gives nothing to detect them with.
10. Leaving the second whole-workspace `build` group of a batch for a following batch stays (line 15 of nxr-5rrkay), now checked as the batch ends: a task that the batch neither reported nor left out fails, and so do all tasks left out where the batch reported none. Only what the batch itself can see is checked at run time; that Nx stores one wave before it starts the next rests on the supported Nx major and the regression tests, with no check of Nx's patch version (worker of nxr-k63csj, accepted at integration). Rests on `DES-BATCH` ("Tasks left for a following batch") and `EVD-NX-24-BATCHES`. Undo: fail instead of leaving out, as line 15 of nxr-5rrkay says.
11. Two limits of leaving tasks out that the review found were not fixed in nxr-k63csj but stated in `DES-BATCH` and split off (control plane): a cached task outside the batch can store what it made of a later build's files (nxr-yfh7zh, under 0.6, high priority), and a build left out keeps its early hash (nxr-f04xen, backlog, with the open question whether that can give a wrong hit). Rests on `GOAL-TRUSTED-CACHE`. Undo: none; both are open issues.
12. Nx's terminal UI is not in the regression tests of leaving tasks out, because the harness cannot yet drive it to its end; nxr-h411yj under 0.6 covers it (worker of nxr-k63csj, accepted). Rests on `VER-BATCHING`. Undo: close nxr-h411yj.
13. The build input check will get a fresh file list in a batch by clearing Nx's own workspace context (`resetWorkspaceContext`) once after each group's cargo call, not by a file walk of the plugin's own (control plane, after a Gemini second opinion on nxr-1tmme6; both options touched a rule for workers: the first clears a process-wide singleton of Nx and adds a private export, the second re-implements which files Nx sees and leaves the task's input files stale). Rests on `GOAL-TRUSTED-CACHE`, `DES-BUILD-INPUT-CHECK` and `RISK-UPSTREAM-CHANGES`. Undo: list in a short-lived child process per group check instead; the reasons are in nxr-1tmme6.
14. A batch builds each task's dotenv layer on a copy of its environment from three functions of Nx's `task-env` module (`unloadDotEnvFile`, `getEnvFilesForTask`, `loadAndExpandDotEnvFile`) instead of calling `getTaskSpecificEnv` around a write to `process.env`; the plugin repeats three facts of Nx's wrapper (the root file names, the order of the calls, the load switch), and a test fails when the wrapper's source changes in the installed Nx (worker of nxr-4sr6hd; kept by the control plane after the review raised the new private export as a stop trigger, because it swaps one export of an already loaded module for another and is what the issue asked for). Not chosen: `getGraphTimeDotEnvForTask`, keeping the write with checks, a child process. Rests on `DES-BATCH` ("Dotenv files"), `VER-BATCHING` and `RISK-UPSTREAM-CHANGES`. Undo: call `getTaskSpecificEnv` around the shield again.
15. dotenv's vault parsing inside Nx's loader still writes `DOTENV_VAULT_<NAME>` to the live environment, in the `nx` process as in a batch; the plugin does not shield `process.env` against it, and the effect (the raw value can reach other tasks' cargo, differently in a batch for one task order) is a stated limit and the backlog issue nxr-gcknzm (control plane; it needs `DOTENV_KEY` and a vault beside a task's dotenv files). Rests on `DES-BATCH` and `GOAL-TRUSTED-CACHE`. Undo: start nxr-gcknzm.
16. Seven issues that speed the test suites up were added to 0.6 on 20 November 2026 at the maintainer's own request in the thread "Review and speed up nx-rust test suite" (nxr-krddfp, nxr-11vr5k, nxr-ryhjf1, nxr-v67m3s, nxr-gabd3d, nxr-ffjvc9, nxr-yatbsx); none blocks the module split nxr-w6117m. The control plane added two edges: nxr-ryhjf1 after nxr-aqgka5 (both change the end-to-end spec) and nxr-gabd3d after nxr-krddfp (it reuses its helper). The changes of `VER-TARGET-DEFAULT-GUARD` and `VER-SETUP` in nxr-yatbsx are the maintainer's, approved in that thread. Undo: cancel the issues not yet started.
17. Runtime inputs (worker of nxr-aqgka5, accepted at integration, with the review's points decided by the control plane): the variables input prints one escaped line per variable from awk's `ENVIRON` and ends with a fixed line, which changes the keys of ordinary values (accepted because the plugin is not published, `ADR-PUBLISHING-AT-1-0`); every input that can fail ends in a fallback that needs no program besides `sh`; a failing script input keeps a random key and the task gets a warning from the executor's own rerun of the command, at about 30 ms and one more `cargo metadata` call per `build` or `doc` that actually runs (cost accepted by the control plane: a cache that silently never hits is worse); a warning and not a failed task, since Nx gives a runtime input no way to fail a task; the `sh` to `node` to `cargo metadata` chain for artifact folders stays (about 29 ms, nothing exact was cheaper, and reading cargo's configuration would re-implement cargo); the test-mode record that hashing writes stays (the only channel from hashing to the executor). Exotic cases are the backlog issues nxr-ntvnds and nxr-563kcq. Rests on `DES-INPUTS`, `DES-TEST-MODE`, `EVD-RUNTIME-INPUT-SCRIPTS` and `GOAL-TRUSTED-CACHE`. Undo: drop the rerun in `runtime-input-check.ts` to save its cost; the key format has no undo worth having.
18. After the reset of line 13, Nx's new workspace context can still take over the file walk of another Nx process that is walking the repository at that moment, so the build input check can list a folder as it was before the group's cargo call; accepted as a stated limit and left to the backlog as nxr-tfha8g (control plane, after the review of nxr-1tmme6 found it by reading Nx's source and the worker confirmed it; it needs two Nx processes at work at once with a walk of milliseconds overlapping the check's start, and the only switch is an environment variable). Rests on `DES-BUILD-INPUT-CHECK` (point 5), `EVD-NX-24-WORKSPACE-CONTEXT`, and the limit already accepted for commands that run at once (`ADR-TEST-AFTER-BUILD`). Undo: start nxr-tfha8g (a short-lived child process per group check, or an option asked of Nx).
19. The test harness pre-builds the third-party crates of the `napi-addons` and `wasm-packages` fixtures once per run and removes the workspace's own crates from that template with cargo's own `cargo clean -p`, against a target directory that is given explicitly inside the template; it keeps no model of cargo's build layout, and refuses to remove a path outside its own folder (control plane, after the review of nxr-krddfp found that the first version read cargo's private layout and could delete another project's output under a shared `build.target-dir`). On Cargo 1.91 `cargo clean -p` leaves the incremental folders of the members' build scripts, which the compiler ignores in a copy. The root `package.json` gained the dev dependency `@jest/test-sequencer` for the test order. Rests on `VER-ARTIFACTS`, `VER-BUILD-INPUT-CHECK` (no item changed). Undo: drop `warmBuilds` in `nx-rust/test/harness/fixture-builds.ts`; the tests then build cold again.
20. The release and lockfile specs share one test registry server per spec file, reset before each test, and the daemon cases of `caching-runs.spec.ts` and `artifact-folders.spec.ts` keep a workspace each, against one item of nxr-11vr5k: the worker built the shared workspace and measured no gain, since a cold build of that fixture takes about 0.3 s (worker, accepted by the control plane). That the two hold cases of `test-after-build.spec.ts` cannot fail in their default batched run is older than the change and is nxr-7v04ge, under 0.6. Rests on `VER-RELEASE` (wording only). Undo: none needed.
21. The memo of baseline hashes that nxr-v67m3s asked for is not kept (control plane): keyed by the real starting state only 13 rows share a baseline, and the memo with its confirmation step saved 17 of 281 inspector runs and about 2 of 66 seconds, the size of the run-to-run variation, at the price of a keyed cache with purity rules in the harness of the test that guards `VER-CACHE-KEYS`. The plugin-version test's use of the compiled plugin was measured alone on 21 November 2026 and saved 0.18 s in the median, so it was reverted too: nxr-v67m3s closed with the finding and no change to source or tests (f7f2de8). Undo: file a new issue for the memo; its design and its three checks are described in the summary of nxr-v67m3s.
22. Staged builds (the maintainer's choice of 20 November 2026, recorded in `ADR-STAGED-BUILDS`): the control plane settled two points the choice left open. The stage lies inside the artifact directory (`<artifact dir>/.nx-rust-stage/<pid>-<n>`), not under `.nx/workspace-data`: the same file system as the files it replaces, the build input check already skips cargo's directories, and `cargo clean` removes it. Provisional, because users can see it: with nothing left for a following batch, a later build group of one batch process still runs and is stored after an earlier group failed under `--nx-bail`, as other groups of one batch do today, unless Nx tells the executor about the flag through its public arguments. Rests on `DES-BATCH` ("Staged builds") and `EVD-STAGED-BUILDS`. Undo: move the stage; or stop later groups after a failure once Nx offers the flag.

23. The dotenv check of nxr-qkxcmm (a2e5f4d). The maintainer chose "Static, cycles allowed (Recommended)" on 20 November 2026, which `DES-BATCH` ("Dotenv files") quotes. The control plane settled what that left open: the check follows the matching, splitting, escaping and replacing of the `dotenv-expand` that Nx has installed, with no pin to version 12.0.3 at run time; a test holds the source text of that library and fails with instructions when it changes (`RISK-UPSTREAM-CHANGES`, `EVD-DOTENV-STATIC-CHECK`). An earlier instruction to count an even number of backslashes as unescaped was withdrawn in favour of the library's own rule. The advice to run with `--batch=false` was removed from the check's row in `DES-DIAGNOSTICS` and from the guide, because the check runs the same way with and without batches. Known limit, in the backlog as nxr-vwpjg2: a batch builds a task's dotenv layer before the check runs. Undo: revert a2e5f4d, which brings the follower of 12.0.3 and its pin back.

24. The two hold cases of `test-after-build.spec.ts` show the order of `test` after `build` with a run that schedules task by task (`--batch=false`) in place of the batched run, which held the test back with or without the dependency (worker of nxr-7v04ge, accepted by the control plane; 3e90020). `VER-TARGETS` and `DES-TARGETS` do not change, and the batched run stays covered by the other cases of the file. Undo: revert 3e90020.

25. Staged builds, integrated as 4bf2195 (nxr-yfh7zh). The reworked change got a first review of its own (`xhigh`) and one re-check. The control plane settled these points after the review:
    - The refusal of two `build` tasks of one crate into one folder judges by the outputs that Nx resolved for the tasks of the command, not by the tasks' options: the first version compared raw options, missed the same folder under different spellings and rebuilt Nx's option merging for the other tasks. A build whose outputs name nothing is not judged, and two uncached builds whose outputs name one folder are refused even where their own dotenv files move their artifact directories apart (`DES-BATCH`, "Files that a batch stores"). Undo: none sensible; the earlier comparison is in the history of the branch only.
    - Stated limit, which the maintainer may want closed: where Nx restores every such task from its cache, no executor runs and none is refused; each cache entry holds its own build's files, and the folder holds those of the task restored last. Reaching it needs both builds warmed in separate commands first. Where one is restored and the other runs, the one that runs is refused. Undo: file an issue for a check that also sees restored tasks.
    - A file that cannot be moved out of the stage fails the task of its crate, not every task of the group; the texts of `DES-BATCH` and `DES-DIAGNOSTICS` were aligned with the code. Undo: fail the group in `staged-run.ts`.
    - Wording only, no code: a folder below the artifact directory that is a symbolic link is followed by a move, as cargo follows it; a stage that an interrupted command left is read by Nx where a Cargo directory in a project's folder is not ignored by git, which `DES-DIAGNOSTICS` already warns of; crates whose final files share a name stay the exception of `DES-OUTPUTS`; whether a stage's process runs is judged in the process namespace of the command that looks (`ADR-STAGED-BUILDS`).
    - Accepted as it is: where two tasks declare the same directory itself as an output, the refusal message names its parent folder.
    - Observed, nothing filed: a dashed `--target-triple=<host>` on the command line reaches neither the executor nor the outputs on Nx 24.0.6, so cargo builds the default target and Nx stores that folder; the stored files are right, and the flag is ignored without a message.

26. The shared test registry answers every request with `Connection: close` (nxr-04ezzm, e6669f1; control plane). A test that uploads right after the registry's reset failed with `fetch failed` / `read ECONNRESET` in two of five full uncached runs of the unit suite on 21 November 2026, always under load from other suites; the worker could not reproduce it in five full runs of its own or on the spec alone. The header goes in without a failing reproduction, because both candidate causes need a reused connection and it removes the reuse, adds no retry and made no spec slower. It is unverified: if the failure shows again, the cause is elsewhere, and the archived issue says to record the full error with its `cause` chain first. Undo: revert e6669f1.

27. The end-to-end suite and its CI jobs (nxr-ryhjf1, 94c998d). Not verified until the maintainer pushes: the workflow cannot run from a worktree. In the first run, check that `e2e-stable` and `e2e-msrv` start at the same time, that `./.github/actions/e2e` resolves after the checkout and each job prints its own `cargo --version`, and that `End-to-end tests` reports, shows both results and satisfies the branch protection; cancel one toolchain job once to see the check fail.
    - The two toolchains are two jobs of their own behind the required check `End-to-end tests`, which fails unless each one's result is exactly `success`, in place of the matrix the issue named (control plane, after the review): GitHub does not document how the legs of a matrix are combined into one result, and a public run showed a check of that shape pass with one leg cancelled. Their steps are one local composite action. Undo: revert 94c998d, which brings back the single job that ran the suite twice.
    - Each run publishes the plugin under a version of its own and installs exactly that one, in place of wiping pnpm's cache (worker, accepted): removing only the plugin's cache entry would rest on pnpm's cache layout.
    - `AGENTS.md` now says "both required checks" and names them, since the workflow has four jobs of which two are required.
    - The gain on this machine is 2 to 4 seconds per run; the time saved in CI is a projection.

28. Terminal runs of the test harness (nxr-h411yj, c6f1464). The harness gives terminal runs `TERM=xterm-256color` and a size where a way of running opens Nx's terminal UI: with `TERM` unset or `dumb`, as in agent shells, the terminal UI of Nx 24.0.6 stays open until a timeout (worker; `EVD-NX-24-BATCHES`, "Tasks left out"). The control plane settled two points after the review:
    - "dynamic in a terminal" and "the terminal UI" both stay among the 11 ways of running, although on Nx 24.0.6 both reach the same renderer through different flags: the maintainer decided on 20 November 2026 that the ways are not narrowed, and they are two different commands a user types. `VER-BATCHING` says so. Undo: drop or change one way in `batch-runs.spec.ts`, which is the maintainer's call.
    - The new terminal-UI case in `batch-builds.spec.ts` asserts that one batch process runs both `build` groups. That cargo's lines are shown live under the terminal UI is not asserted there, because the terminal UI shows only its task list until a key opens a pane; the unit test of `batchLiveOutput` stays the check, and `VER-BATCHING` no longer claims more.
    - `EVD-NX-24-BATCHES` now says that its earlier `dynamic` and terminal-UI runs had fallen back to another output style; the rerun through the real terminal UI found the same three differing variables and nothing else.
